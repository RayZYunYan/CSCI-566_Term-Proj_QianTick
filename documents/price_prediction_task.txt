# Price Prediction Task

Our price prediction module is formally defined as a deep learning classification pipeline for short-term stock movement prediction. 
The objective is to predict whether a stock will move up or down on the next trading day, using only information available up to the current day. 
Within the team structure, the price group is responsible for the complete price-side pipeline, while the news group is responsible for the news-side encoder. 
The final team system will align both sides under the same stock identity, the same prediction time, and the same target horizon, so that the two modalities can later be fused in a downstream cross-attention layer.

In the data preparation stage, the pipeline uses yfinance to download daily OHLCV data for a basket of target stocks and several market-context tickers. 
The raw fields include Open, High, Low, Close, Adj Close, and Volume, and the merged raw output is stored as a unified stock table. 
Rather than treating each stock as a fully isolated forecasting problem, the pipeline organizes multiple tickers into one pooled supervised learning dataset. 
This design increases sample size, supports more stable model comparison, and allows the model to learn price patterns across different stocks while preserving ticker-level metadata. 
Market context tickers such as SPY, QQQ, ^VIX, XLK, SOXX, and TLT are still considered part of the price side, because they are external price signals rather than text or news features.

The task is formulated as a binary classification problem. 
For each sample observed at time t, the label is defined by comparing Close[t+1] and Close[t]. 
If Close[t+1] > Close[t], the label is 1; otherwise the label is 0. 
This definition is used consistently throughout feature construction, dataset building, model training, evaluation, and fusion export. 
To avoid leakage, all input features must be constructed strictly from information available at or before day t, and train / validation / test splits must remain chronological.

During feature engineering, the raw OHLCV records are transformed into a unified feature table. 
The pipeline computes two groups of features for each ticker: sequence-style price features and technical indicator features. 
The sequence-style features include price changes relative to the previous close, daily returns, log returns, intraday range, open-close change, volume change, log-volume, and rolling statistics. 
The technical indicator group includes SMA, EMA, RSI, MACD, Bollinger Band features, ATR, momentum, and volume ratio features. 
These two groups are not sent into separate model branches. Instead, they are merged into one deduplicated feature set and then organized into a rolling 30-day window, producing a unified input tensor with shape (N, 30, num_features). 
This means the sequence models all observe the same combined price-and-indicator representation over time. 
Feature engineering itself performs no normalization. Normalization is postponed until after time-based splitting, and only training-set statistics are used.

In the dataset building stage, the merged feature table is converted into supervised samples. 
For each ticker, the pipeline slides a 30-day lookback window over time and uses the next day as the prediction target. 
All samples from all tickers are then concatenated, sorted by prediction date, and split chronologically into train (70%), validation (15%), and test (15%) sets. 
The output includes normalized arrays for X and y as well as metadata tables containing ticker, as_of_date, and target_date. 
The metadata is important because it keeps every sample traceable and provides the alignment key required by the downstream fusion module.

For modeling, the final price-side architecture contains three deep learning sequence models: LSTM, GRU, and TCN. 
LSTM serves as the classic recurrent baseline for temporal dependency modeling, GRU provides a lighter recurrent alternative with strong efficiency, and TCN provides a convolution-based temporal encoder with causal and dilated convolutions for long-range dependency capture. 
All three models consume the same unified rolling-window input and follow the same interface: a forward pass that produces a classification logit, and an extract_features() mode that outputs the hidden representation before the classifier head. 
The probability of upward movement P(up) is obtained by applying sigmoid to the model logit, and the final hard label is produced by thresholding that probability. 
The final system is therefore designed around three parallel price encoders whose hidden representations can be evaluated independently and exported jointly.

The training and evaluation procedure is designed to be uniform across price models. 
Each model is trained with BCEWithLogitsLoss, uses chronological train / validation / test splits, and searches hyperparameters with Optuna. 
The search space includes hidden dimension, number of layers, dropout, learning rate, batch size, weight decay, and activation function. 
Validation ROC-AUC is used for early stopping and pruning during hyperparameter search. 
After the search phase, the best hyperparameter configuration is used to retrain the final model, and then evaluation on the held-out test set is reported with Accuracy, Precision, Recall, F1-score, ROC-AUC, and the confusion matrix. 
The probability threshold is selected on the validation set so that final classification decisions are based on a tuned operating point rather than an arbitrary default threshold. 
All metrics are saved through a shared metrics module so that different models are evaluated under the same standard.

At the engineering level, the pipeline is modular. 
fetch_data.py downloads and cleans raw stock data; feature_engineering.py constructs the full unnormalized feature table; dataset_builder.py builds rolling-window supervised samples and applies train-only normalization; lstm_model.py, gru_model.py, and tcn_model.py encapsulate the three price-model training pipelines; metrics.py centralizes evaluation utilities; fusion_interface.py exports price-side feature vectors and prediction metadata for the fusion stage; and main_pipeline.py acts as the single orchestration entry point. 
Each stage writes artifacts to disk so that the workflow remains reproducible and stages can be rerun independently when needed.

From the perspective of deliverables, the price-side module produces more than just standalone classifiers. 
It provides a complete supervised-learning dataset construction process, three trained sequence models, standardized evaluation outputs, and a fusion-ready export interface. 
The final export contract is defined around the three trained price encoders in the pipeline. 
Accordingly, the exported price-side outputs should include LSTM, GRU, and TCN feature vectors together with aligned metadata and probability columns. 
This makes the price module usable both as an independent benchmark system and as a structured upstream component for the team's multi-modal fusion stage.

In summary, the final price prediction pipeline is a complete engineering workflow for next-day stock direction classification built on price-only information. 
It starts from yfinance data collection, constructs unified rolling-window price features, builds leakage-safe chronological datasets, trains three sequence models under a shared protocol, evaluates them with standardized metrics, and exports aligned hidden representations and probabilities for downstream fusion. 
The system therefore serves both as the standalone price-side learning module and as the price representation provider for the team's final fusion architecture.

我们的 price prediction 模块被正式定义为一个面向股票短期方向预测的深度学习分类 pipeline。任务目标是：只使用当前时刻及之前能够观测到的价格信息，
预测下一交易日股票是上涨还是下跌。在团队分工中，price 组负责完整的价格侧 pipeline，news 组负责新闻侧编码器。最终整个团队系统会在同一只股票、同一个预测时点、
以及同一个目标时间跨度上完成对齐，然后再在下游 cross-attention 融合层中把两侧信息结合起来。

在数据准备阶段，pipeline 通过 yfinance 下载多只目标股票以及若干市场环境 ticker 的日频 OHLCV 数据。原始字段包括 Open、High、Low、Close、Adj Close 
和 Volume，最终合并成统一的原始价格表。这里的设计不是把每只股票完全当作一条孤立时间序列去处理，而是把多只股票一起组织成一个统一的监督学习样本池。这样做
可以扩大样本量，提升模型比较的稳定性，同时仍然保留 ticker 级别的 metadata。像 SPY、QQQ、^VIX、XLK、SOXX、TLT 这类市场环境 ticker 仍然属于 price side，
因为它们本质上是外部价格信号，而不是文本或新闻特征。

这个任务被统一定义为一个二分类问题。对于任意一个在时刻 t 构造出来的样本，我们通过比较 Close[t+1] 和 Close[t] 来定义标签。若 Close[t+1] > Close[t]，
则标签为 1；否则为 0。这个定义会在特征构造、数据集构建、模型训练、模型评估以及 fusion 导出中保持一致。为了避免信息泄漏，所有输入特征都必须严格只依赖于
t 时刻及之前能够看到的信息，并且 train / validation / test 的切分必须保持时间顺序。

在 feature engineering 阶段，原始 OHLCV 数据会被转换为统一的特征表。pipeline 会为每个 ticker 计算两组特征：一组是序列型价格特征，另一组是技术指标
特征。序列型特征包括相对于前日收盘价的价格变化、日收益率、对数收益率、日内波幅、开收差、成交量变化、对数成交量以及滚动统计量。技术指标特征包括 SMA、EMA、
RSI、MACD、布林带相关特征、ATR、动量和成交量比率等。这两组特征不会被送进两个分离的模型分支，而是先合并成一个去重后的统一特征集合，再组织成 30 天滑动窗口，
形成 shape 为 (N, 30, num_features) 的统一输入张量。也就是说，所有时序模型看到的都是同一套价格 + 指标的组合表示。feature engineering 本身不做任何归一化；
归一化会被推迟到按时间切分之后，并且只使用训练集统计量。

在 dataset building 阶段，合并后的特征表会被转换成监督学习样本。对于每个 ticker，pipeline 都会在时间轴上滑动一个 30 天 lookback window，并把下一天作为
预测目标。之后将所有 ticker 的样本拼接起来，按照预测日期排序，再按时间顺序切分为 train（70%）、validation（15%）和 test（15%）。输出既包括归一化后的 X 和 y，
也包括 metadata 表，其中记录了 ticker、as_of_date 和 target_date。metadata 非常重要，因为它既保证每个样本可追踪，也构成了后续 fusion 模块所需的对齐键。

在模型层面，最终的 price-side 架构包含三个深度学习时序模型：LSTM、GRU 和 TCN。LSTM 作为经典的循环时序基线，负责建模时间依赖；GRU 提供更轻量、更高效的循环替代；
TCN 则通过 causal convolution 和 dilated convolution 提供卷积式时序编码能力，用于捕获更长距离的时间依赖。三个模型都消费同一个统一的滑动窗口输入，并遵循同一套接口：
forward() 输出分类 logit，extract_features() 输出分类头之前的隐藏表示。上涨概率 P(up) 由 logit 经过 sigmoid 得到，而最终的硬分类标签则由这个概率再经过 threshold
得到。因此，整个最终系统被设计成三条并行的 price encoders，它们既可以被独立评估，也可以把隐藏表示一起导出给 fusion 使用。

训练与评估流程在不同价格模型之间保持统一。每个模型都使用 BCEWithLogitsLoss，使用严格按时间顺序划分的 train / validation / test，并通过 Optuna 搜索超参数。
搜索空间包括 hidden_dim、num_layers、dropout、learning_rate、batch_size、weight_decay 和 activation function。validation ROC-AUC 被用作超参搜索中的
early stopping 和 pruning 指标。搜索结束后，再用最佳超参重新训练 final model，最后在 held-out test set 上报告 Accuracy、Precision、Recall、F1-score、
ROC-AUC 以及 confusion matrix。概率阈值会先在 validation set 上选择，从而保证最终分类决策基于调优后的 operating point，而不是随意固定的默认阈值。所有指标都
通过共享的 metrics 模块保存，从而保证不同模型是在同一评估标准下进行比较。

从工程结构上看，这个 pipeline 是模块化的。fetch_data.py 负责下载和清洗原始股价数据；feature_engineering.py 负责构造完整的未归一化特征表；
dataset_builder.py 负责构建滑动窗口监督学习样本并进行 train-only 归一化；lstm_model.py、gru_model.py 和 tcn_model.py 封装了三个价格模型的训练流程；
metrics.py 统一评估逻辑；fusion_interface.py 负责导出价格侧特征向量和预测 metadata；main_pipeline.py 则作为唯一的总入口，负责串联整个流程。每个阶段都会把产物写到
磁盘上，因此流程具备良好的可复现性，也便于单独重跑某个阶段。

从交付物角度看，price-side 模块不只是若干个独立分类器。它同时提供完整的数据集构建流程、三个训练好的时序模型、标准化评估结果，以及供 fusion 使用的导出接口。
最终的导出合同将围绕 pipeline 中三个训练好的 price encoders 来定义。因此，price-side 的最终导出结果应当包括 LSTM、GRU 和 TCN 三组特征向量，以及对齐后的
metadata 和对应的概率列。这使得 price 模块既可以作为一个独立 benchmark 系统存在，也可以作为团队多模态融合阶段的标准上游组件。

总结来说，最终的 price prediction pipeline 将构成一个完整的、面向 next-day stock direction classification 的工程工作流。它从 yfinance 数据抓取开始，
构建统一的滑动窗口价格特征，生成防止泄漏的时序数据集，在统一协议下训练三个时序模型，用标准化指标做评估，并把对齐好的隐藏表示和概率导出给下游 fusion。也就是说，
这个系统同时承担了 price-side 独立学习模块和团队最终融合架构中 price representation provider 的双重角色。
